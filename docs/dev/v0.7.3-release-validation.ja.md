(#652/#664) による降格 (likely → maybe、warning → info) であり、`--strict` で

### fastmcp の新規検出 (v0.7.3 で初出、HEAD でも残る)

`examples/**` が entry root になった (#666) ことで、examples の import が root の
`pyproject.toml` を基準に判定されるようになった。

- CHK004 ×46: `rich`、`pydantic`、`typing-extensions`、`pydantic-settings`、`mcp` を
  examples が直接 import している。root の依存には transitive でしか入らないが、
  examples は配布物ではないので error/certain は過剰。
- CHK010 ×26: `examples/atproto_mcp`、`examples/smart_home`、`examples/testing_demo` は
  自前の `pyproject.toml` を持つ独立 project。その依存 (`atproto`、`phue`、
  `androidtv`) と相対的な `server` モジュールが root から解決できない。
- CHK005 ×4、CHK003 ×2: 同じく examples の `opentelemetry-sdk`、`psutil`、`PIL`、`qrcode`。
- llama_index でも examples の `dotenv` が CHK003 ×2 として出る (oss-metrics gate 6 の +2)。

precision-gap-analysis の P6c (入れ子 pyproject) と P9-4 (examples の文脈) に該当する。

## 手順上の注意 (今回判明)

同一 version の worktree (v0.7.3 tag と main、どちらも `0.7.3`) を同じ
`CARGO_TARGET_DIR` でビルドすると、cargo が lib の rlib (`chokkin-42f501d6…`) を
fingerprint 一致とみなして再利用し、main のビルドが tag のロジックで動く。
今回は HEAD の初回計測が v0.7.3 と完全一致したことで気付き、`target-head/` を
分けて再ビルドして確認した。release validation の手順では version ごとに
`CARGO_TARGET_DIR` を分けること。

## 次リリースに向けた改善ステップ

優先度は「corpus 上の件数 × 誤検知率 × 修正の局所性」で付けた。
S1〜S3 を次のパッチリリース、S4〜S7 をその次、P-A〜P-E は並行して進める。

### S1 (高): examples/docs の import を依存ルールから切り離す

対象: fastmcp CHK004 +46 / CHK010 +26 / CHK005 +4 / CHK003 +2、llama_index CHK003 +2。

1. `examples/**`、`docs/**` 由来の entry は CHK001 の到達性にだけ使い、
   CHK003/004/005/010 では `ImportContext::Dev` (または新設の `Examples`) として
   info に落とす。#689 が notebook にだけ入れた扱いを `.py` にも広げる。
2. 入れ子の `pyproject.toml` を持つディレクトリ (`examples/atproto_mcp` 等) は
   独立 project として親の解析対象から外す (P6c)。`--probe` に
   「nested projects: N (skipped)」を出す。
3. `scripts/oss-expectations.tsv` に fastmcp の CHK004 / CHK010 上限を追加し、
   oss-metrics の gate 6 が再び 137 に戻ることを確認する。

### S2 (高): CHK004 の confidence を証拠の強さで分ける

対象: 1,980 件 (airflow 918、llama_index 549、langchain 262)、coverage 2.7%。

1. member 自身の lock に transitive として存在 = `likely`、root lock にのみ存在 =
   `maybe`、extras 経由でしか入らない = info。現状はほぼ error/certain。
2. `sample-precision-labels.py` で CHK004 を 200 件サンプルして label を付け、
   precision を測ってから閾値を決める (今は 54 件の 100% しかない)。

### S3 (中): CHK010 の optional 判定を関数内 import とガード付き import に広げる

対象: HEAD で 512 件 (transformers 206、llama_index 102、mlflow 78)。

1. `importlib.util.find_spec()` / `is_*_available()` の分岐内、`raise ImportError`
   の直後の import は optional (P6a の拡張)。llama_index gaudi の
   habana_frameworks / deepspeed / peft がこのパターン。
2. transformers の `is_torch_available()` 系は bundled map ではなく
   「同モジュール内で `*_available` を呼ぶ関数の中の import」として一般化する。
3. 残る map gap は #688 で追加した bundled map の手順に沿って corpus から拾う。

### S4 (中): CHK008 の使用証拠を広げる (precision 14%)

label 50 件中 43 件が fp。P5 の self-referential usage (同じ module 内の
文字列参照、`__all__`、decorator 登録) を使用として数える。113 件は 3 バージョンで
不変なので、修正後の差分がそのまま効果測定になる。

### S5 (中): CHK009 の意図的な重複宣言を info にする (precision 0%)

transformers 7 件、mlflow 4 件は extras ごとに同じ specifier を宣言している
パターン (P10)。specifier が一致する重複は info、矛盾する場合だけ warning にする。

### S6 (中): CHK007 の label を取り直す

HEAD では #687 で 52 → 2 件になる。label 14 件はすべて fp で、修正後に stale に
なるので relabel する。残り 2 件 (llama_index) を確認して tp/fp を付ける。

### S7 (低): CHK006 の app mode 残件

mlflow 158、airflow 267、fastmcp 60、poetry 29。plugin registry
(entry points)、Django signal、click group の登録を「外部からの参照」として扱う。
`modular_*.py` / alembic と同じ規約テーブルに追加する形で局所的に直せる。

### P-A: label と expectations の更新

- CHK001 の stale label 12 件 (django 等、maybe に降格) を `--strict` 出力で
  付け直す。
- CHK004 / CHK006 / CHK010 の coverage (2.7% / 5.7% / 7.2%) を 20% 以上に上げる。

### P-B: oss-metrics に「降格」と「消失」を区別する gate を入れる

v0.7.3 のように warning 件数が 6,588 → 3,741 に動くと、gate は件数しか見ないので
消失と降格を区別できない。`--strict` でも採取し、「strict で消えた findings 数」を
別列にして上限を置く。

### P-C: rule 別 precision の下限を gate にする

現在は「recorded only」。CHK002 95%、CHK003 90% は既に満たしているので
まずこの 2 つに閾値を置き、CHK008/009 は S4/S5 の後に追加する。

### P-D: metamorphic property を corpus で回す

- `examples/**` を削除しても root package の CHK003/004/010 件数は変わらない
  (S1 の受け入れ条件)。
- 依存を lock に追加しても CHK004 は増えない。
- `--strict` の findings は既定 filter の findings の上位集合である。

### P-E: release validation 手順の更新

`docs/dev/v0.7.1-release-validation.md` の手順に、version ごとの
`CARGO_TARGET_DIR` 分離と、tag 間の finding-level diff (fingerprint 単位の
NEW / GONE / CHANGED) を追加する。

## 実行コマンド

```sh
# tag ごとに worktree と target dir を分けてビルド
git worktree add "$S/wt-0.7.2" v0.7.2 && (cd "$S/wt-0.7.2" && CARGO_TARGET_DIR="$S/target-072" cargo build --release --locked)
git worktree add "$S/wt-0.7.3" v0.7.3 && (cd "$S/wt-0.7.3" && CARGO_TARGET_DIR="$S/target-073" cargo build --release --locked)
CARGO_TARGET_DIR="$S/target-head" cargo build --release --locked

# corpus
scripts/clone-oss-fixtures.sh
for p in $(cut -f1 scripts/oss-clones.manifest); do
  "$BIN" --reporter json --no-exit-code --no-cache target/oss-clones/$p > out/$p.json
done
python3 scripts/oss-metrics.py --bin "$BIN" --runs 1 --output "$S/metrics/0.7.3" --baseline "$S/metrics/0.7.2"

# 降格の確認
chokkin-0.7.3 --reporter json --no-exit-code --no-cache --strict target/oss-clones/django
```
