# v0.3 stocktake — per-rule label coverage (issue #85 WS1)

First full-corpus inventory of what chokkin actually reports across **all**
CHK rules on the §17 OSS validation set, and how much of it is backed by
ground-truth labels. This is workstream 1 of issue #85 (quantifying detection
effectiveness before the v1.0 freeze): measure the blind spots first, decide
remediation afterwards.

- chokkin version: `0.3.0`
- date: 2026-07-04
- harness: `scripts/clone-oss-fixtures.sh` + `scripts/oss-metrics.sh`
  (now classifies every finding, not just CHK002/CHK003)
- validation set: `scripts/oss-clones.manifest` (20 projects, pinned tags)
  + 2 in-repo recall sentinels
- ground truth: `scripts/oss-fixtures.labels.tsv` (157 rows, all CHK002)
- confidence floor: `likely` (CLI default, `src/config/defaults.rs`) —
  `maybe`-confidence findings are **not** part of this measurement

## What the unknowns look like

Manual inspection of `target/oss-metrics/findings.tsv` (not yet labelled —
verdicts below are impressions to guide triage, not ground truth):

- **CHK001 (1,265)** — dominated by django (1,026) and black (207). Mostly
  test-suite and fixture files not reachable from entry roots (e.g. requests
  `tests/compat.py`, django's per-app test modules). Whether test files
  should count as "unused" is a policy question before a labelling question.
- **CHK002 (2)** — zero live findings on the 20 OSS projects; only the two
  sentinels fire. The Phase 1.5 remediation cleared the corpus, which means
  the FP gate is green but exercises almost nothing. The 155 historical `fp`
  labels no longer match any finding.
- **CHK003 (963)** — recurring clusters: fastapi tests importing `docs_src.*`
  tutorial modules; django's Selenium-based admin tests (test deps declared
  in `tests/requirements/`, not in packaging metadata); werkzeug importing
  `_typeshed.wsgi` (type-checking-only module); optional imports like
  `cryptography.hazmat`. Most clusters look like fixture-layout or
  typing-only patterns rather than genuinely missing runtime deps.
- **CHK004 (0)** — the corpus never triggers the rule. No statement about
  its precision is possible; it needs a dedicated fixture (see next
  actions).
- **CHK005 (7)** — all "used from runtime code but only declared in dev",
  and all seven are optional-import patterns (httpx→trio,
  python-dotenv→ipython, fastapi→anyio, djangorestframework→markdown/
  pygments/pyyaml/inflection). Verdict depends on the intended rule
  semantics for `try/except`-guarded imports.
- **CHK006 (13,219, 79% of everything)** — public symbols of library code
  not referenced from outside their module. On a corpus made of libraries,
  the public API is *by design* externally consumed; e.g. requests'
  `BaseAdapter` is reported at `warning`. This is the single biggest noise
  source and mostly a severity/library-mode policy question.
- **CHK007 (253)** — same shape as CHK006 for re-exports (e.g. requests'
  exception re-exports in `__init__.py`).
- **CHK008 (100)** — dev tooling binaries referenced from config/CI but not
  declared (black, flake8, isort, mypy, pre-commit, tox across most
  projects). Homogeneous cluster; a handful of labels would cover most of
  it.
- **CHK009 (19)** — all `certain`, all real multi-context declarations
  (runtime+dev or dev+extras, e.g. fastapi's `httpx` in dev and two
  extras). Whether intentional extras-mirroring counts as `tp` is a rule-
  intent decision.
- **CHK010 (870)** — 738 of them are django importing `tests.*`, resolvable
  only because django's test runner mutates `sys.path`. The rest are
  optional/platform modules (playwright, mkdocs, winreg).

## Blind spots

1. **Ground truth exists for one rule out of ten.** Every quantitative
   quality claim chokkin can make today is about CHK002.
2. **The CHK002 gate now measures only sentinels.** 0 live findings on the
   corpus → the FP gate passes on an empty set and recall rests on 2
   fixtures.
3. **CHK004 is never exercised** by the validation set.
4. **`maybe`-confidence findings are invisible** to the harness (default
   floor is `likely`).
5. **CHK006 volume swamps everything else** (79% of findings), so any
   labelling effort ordered by count would be consumed by a rule whose main
   problem is policy (library mode), not precision.

## Harness changes backing this stocktake

`scripts/oss-metrics.sh` now records every finding in `findings.tsv` with a
per-rule stable key (`distribution` for CHK002/005/009, `file:module` for
CHK003/004/010, path for CHK001, `path:symbol` for CHK006/007, binary name
for CHK008), emits a per-rule coverage table (`coverage.md`), and pins the
recall gate to CHK002 `tp` rows so future labels for other rules cannot
silently change the §17 gate. Note: CHK003 rows previously carried a `?` key
(the old harness read the JSON `distribution` field, which is null for
import-subject issues); they are now keyed by import site.

## Suggested next actions (owner decision, feeds #85 WS2+)

1. Label the homogeneous clusters first — CHK008 (dev tools) and CHK009
   (extras mirroring) are small and mechanical; CHK003's four clusters cover
   most of its 963 findings.
2. Decide CHK006/CHK007 library-mode policy before labelling them; volume
   makes label-first infeasible.
3. Add a CHK004 fixture (transitive-only dependency) to the sentinel set so
   the rule is exercised at all.
4. Consider a small number of live CHK002 cases (e.g. a fixture project with
   a realistic unused dep) so the FP gate measures more than sentinels.
