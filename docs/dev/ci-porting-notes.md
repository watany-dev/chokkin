# CI porting notes

This document tracks items ported from `watany-dev/ptuf` that are intentionally
deferred or require manual setup before they become fully effective.

## PyPI Trusted Publishing setup

Trusted Publishing is configured for the released `chokkin` package on PyPI.
For future releases, keep the PyPI publisher and GitHub environment aligned:

1. Go to https://pypi.org/manage/account/publishing/ (or the project page once
   reserved).
2. Add a publisher with:
   - **Repository owner:** `watany-dev`
   - **Repository name:** `chokkin`
   - **Workflow filename:** `release.yml`
   - **Environment name:** `pypi-chokkin`
3. Keep the `pypi-chokkin` environment in the GitHub repository settings
   (Settings → Environments) because `.github/workflows/release.yml` publishes
   through that environment.

The workflow uses `id-token: write` + `pypa/gh-action-pypi-publish` with no
API token — authentication is handled entirely by OIDC. Release actions in
`.github/workflows/release.yml` are SHA-pinned; bump tags by resolving the
commit SHA and updating the inline comment.

## Repository settings checklist

These live in the GitHub and PyPI settings, not in the repository, so review
them when a maintainer, workflow, or job name changes.

**`main` branch ruleset** (Settings → Rules → Rulesets):

- Restrict deletions and block force pushes.
- Require a pull request before merging, with review from Code Owners
  (`.github/CODEOWNERS`). A PR author cannot approve their own PR, so while
  there is a single maintainer, add them to the bypass list (for pull requests
  only) or no maintainer PR can merge.
- Require status checks to pass, with the branch up to date. The jobs that
  cover `make check` (fmt, clippy, test, deny, machete):
  - `Lint (fmt, clippy, doc, machete)`
  - `Test (ubuntu-24.04)`, `Test (macos-14)`, `Test (windows-latest)`
  - `Security (cargo-deny)`

  Require `Semgrep` as well: its scan uses `--error` to fail on findings and
  uploads SARIF even when it fails. The workflow alone does not prevent merging;
  add this exact job name to the ruleset's required status checks.

  Also worth requiring: `MSRV (1.96) + chokkin baseline`,
  `Repo checks (actionlint, generated maps)`, and from the Release workflow
  `Test (dist profile, RUST_TOOLCHAIN)`, `Test action (HEAD wheel)`, each
  `Test wheel (<target>)`, and the `Wheel (<target>)` and `sdist` builds they
  need (a job skipped because a job it needs failed counts as passing). A
  renamed job drops out of the required list silently, so update the ruleset
  in the same PR.

  A PR that only edits prose (`scripts/ci-changes.py`: Markdown under `docs/`
  or at the root, except the READMEs and `docs/dev/spec.ja.md` that tests
  read) skips these jobs, and a skipped job's check passes. The `Test`,
  `Wheel` and `Test wheel` matrices skip their steps instead: a matrix job
  skipped as a whole reports under its unexpanded name and leaves the required
  checks pending. Do not require `Changes`.

**`pypi-chokkin` environment** (Settings → Environments):

- Deployment branches and tags: selected tags only, pattern `v*`.
- Required reviewers: the maintainer. "Prevent self-review" would block the
  only maintainer, so leave it off until there is a second one.

**Releases** (Settings → General → Releases): enable immutable releases.
`release.yml` uploads every asset in the `gh release create` call, so it works
with them unchanged. Releases up to v0.7.0 were published before this was
enabled and are still mutable.

**PyPI** (pypi.org account and the `chokkin` project):

- Two-factor authentication is on for every owner and maintainer.
- The only publisher is the Trusted Publisher above; no API tokens exist for
  the project (Account settings → API tokens), and none are stored as GitHub
  secrets.

## Generated resolver maps

Bundled maps (`src/resolver/bundled/`) and the stdlib table (`src/resolver/stdlib/`)
are generated by `scripts/generate-package-map.py` and
`scripts/generate-stdlib-modules.py`. The CI `check-generated` job reruns both
and fails on drift. Regenerate locally with `make check-generated` after seed or
script changes, and run `make test-scripts` after script changes (requires
Python 3; neither is part of `make check`).

The scripts under `scripts/` (generators, the OSS corpus gates and
`bench-gate.py`) have stdlib-only unit tests in `tests/test_*.py`, run by
`make test-scripts` in the same CI job. They pin the pass/fail boundary of
each gate's judging function on small fixed inputs, so a judgment that
silently always passes fails there; keep a script's judging logic in functions
those tests can call, and `main()` to running tools and wiring results.

Package-map candidates can be harvested from already downloaded, pinned wheel
archives without executing package code:

```bash
python3 scripts/harvest-package-map.py target/map-wheels/*.whl \
  --output target/package-map.candidates.json
```

The harvester does not access the network or edit `data/package-map.seed.json`.
Acquire wheels explicitly (for example with an exact `name==version`), review
the candidate JSON and recorded SHA-256 hashes, then copy accepted mappings into
the seed and run `make check-generated`.

## Coverage threshold

`cargo llvm-cov --fail-under-lines 95` gates both the `make coverage` target
and the `ci.yml` coverage job (lines sit around 98%). It was omitted until the
Phase 1 analyzer provided meaningful coverage. In CI the gate is on the
`--summary-only` step, after the HTML report, so the report artifact is still
uploaded when the gate fails.

## Windows test temp directory

`cargo nextest` on `windows-latest` can hit `PermissionDenied` when many
parallel tests create directories under the default short-path user temp
(`RUNNER~1\AppData\Local\Temp`). The `test` job redirects `TMP` / `TEMP` /
`TMPDIR` to `$RUNNER_TEMP/chokkin-test-tmp` before running nextest.

## Deep property-based tests (`pbt-deep`)

Per PR, the `test` job runs every proptest block at its usual case count:
proptest's default 256, or what the block tunes with
`ProptestConfig::with_cases(chokkin::internals::proptest_cases(n))` when its
cases are slow (a generated project analysed end to end). The `pbt-deep` job
in `ci.yml` runs on the daily schedule instead: `make pbt-deep` sets
`PROPTEST_CASES=4096`, which deepens default blocks to 4096 cases and scales
tuned ones by the same 16x (`with_cases` alone ignores `PROPTEST_CASES`, so a
new tuned block must go through `proptest_cases`). The whole suite took about
25 minutes on a 4-core machine; the job's timeout is 90. A nightly failure reaches
whoever last edited the cron through GitHub's scheduled-workflow notification,
and the `pbt-deep-seeds` artifact holds the seeds proptest saved.

Seed files (`proptest-regressions/**` for in-module blocks,
`tests/*.proptest-regressions` for integration tests) are committed and
reviewed like tests: a seed lands in the PR that fixes the failure it
reproduces, and a run that only probes a hypothesis (a mutation check, a
local experiment) leaves no seed behind.

## cargo-mutants scope

`make mutants` covers all of `src/`. It used to stop at `src/rules/`,
`src/resolver/`, `src/graph/` and `src/fix/`, 22% of the mutants, so the
parser, manifest, plugin and reachability code nobody touched was never
mutated (#1123). All of it is about 6,900 mutants, hours of runner time, so
`.github/workflows/verification.yml` splits it into weekly slices of 12 shards
of at most 100 mutants and runs the slice the ISO week number picks: each
mutant runs once per round (six weeks at that count). `full-mutants` runs this
week's slice on demand, or the one `mutants-slice` names. On a PR only the mutants on the lines the PR changes
(`make mutants-diff`, any file under `src/`). Mutating changed lines alone
runs nothing on a PR that only deletes or weakens tests, so
`scripts/mutants-diff.py` adds every mutant of a file whose tests lost a line:
a `#[cfg(test)]` block's own file, or the source an integration test pins
(`TEST_TARGETS`). End-to-end suites and fixtures pin no narrower code and are
left to the weekly run (#1118). Both fail on a missed mutant
(#837). A failed weekly or full run opens an issue listing its missed
mutants, or comments on the one still open (`mutants-issue`, #1119): GitHub's
scheduled-workflow e-mail alone left a missed mutant on main for days (#1117).
Each shard's summary also lists its timed-out mutants, which count as caught
but may be a missed mutant that only slows a test down. The plan job counts the mutants with
`--list` and splits a PR's run into shards of about 50 (at most 12), so a
large diff still finishes within the 60-minute job timeout. `Mutants` is the one
stable check name to require in branch protection.

Most of a mutant's cost is its rebuild, so the `mutants` job skips
`Swatinem/rust-cache` (its cache never reaches cargo-mutants' scratch copies,
and it exports `CARGO_INCREMENTAL=0`), and the Makefile sets
`CARGO_INCREMENTAL=1` so each mutant is an incremental rebuild of the
baseline. `.cargo/mutants.toml` runs the tests under nextest (one process per
test, so the run is as long as the slowest test) with a 60-second floor on the
per-mutant test timeout, since the auto timeout is 5x the baseline time and a
short baseline would make it tight. The timeout bounds time only, so the
Mutate step also caps each process's data segment at 4 GiB (`ulimit -d`): a
mutant that allocates forever aborts its test (caught) instead of running the
runner out of memory and losing the shard (#1120). A single long test is the floor of every
mutant's test time under nextest, so split an exhaustive test by case family
(as `star_imports_match_cpython_*` is) rather than adding one that runs for
tens of seconds.

A missed mutant is either a missing test (add it) or an equivalent mutant (no
observable behavior changes): exclude the latter in `.cargo/mutants.toml`
`exclude_re` with a comment saying why it is equivalent.

## crates.io

chokkin is distributed via PyPI only (maturin `bin` bindings). Publishing to
crates.io is not planned. The `publish-crates.yml` workflow from ptuf is omitted.

## stop-wrapup hook

ptuf's `.claude/hooks/stop-wrapup.sh` nags `wrapup` when a session that edited
files tries to end. It is not used here: chokkin's `wrapup` follows the
[zghalint](https://github.com/watany-dev/zghalint) shape — a review gate the
developer invokes when the implementation is done — so there is no completion
marker for a stop hook to track. chokkin registers no hooks in
`.claude/settings.json`.
